# AGENTS.md

Notes for AI agents (and people) working in this repo.  Keep this file current: when you learn a build/test step the hard way, add it here.

## Layout
- `mod/src/game` (qagame), `mod/src/cgame`, `mod/src/ui` — the mod.  Replay recorder/playback is `mod/src/game/g_replay.c`; its client side lives in `cgame` (`cg_servercmds.c` `replay_phase`, `cg_draw.c`, `cg_view.c`).
- `iortcw/` — engine, `wasm/` — browser client glue, `omnibot/` — bots, `infra/web/` — nginx pages + Go `status-api` (parses `.rpl` archives in `status-api/replay/parser.go`).
- Replay archives (`.rpl`, format v8) + sidecar `.txt` live in `gamedata/s4ndmod26/replays/` on a server and under `/downloads/s4ndmod26/replays/` on the web host.

## Quick compile check (seconds)
Syntax-check a changed mod file without a full build:
```bash
cd mod/src && gcc -fsyntax-only -w -DGAMEDLL -DCGAMEDLL -I game -I cgame -I ../../third_party/zlib game/g_replay.c
```

## Official builds (Docker)
`make build` / `make populate` (game modules into `gamedata/`), `make wasm-build` then `make wasm-deploy` (browser client).  Docker is not always installed in the dev shell (it isn't in the WSL session used so far) — use the local wasm build below.

## Game and website versions (separate)
- `GAME_VERSION` (`tools/ci/game-version.sh`: `v<date>-<sha>` of the last commit touching the game paths listed there) tags the server image `s4ndmod26` and the client-files image `s4ndmod26-client`, and is the Dockerfile's `VERSION` (pk3 name, `MOD_BUILD_VERSION`). The website image `s4ndmod26-web` is tagged with this commit's version (`WEB_VERSION`, written to `version.txt`); `client-version.txt` holds the game version and is what the launcher manifest reports.
- CI rebuilds the game only when `s4ndmod26:<GAME_VERSION>` and `s4ndmod26-client:<GAME_VERSION>` are not in the registry yet; otherwise the web stage is built with `--build-arg CLIENT_IMAGE=repo.s4ndmod.com/s4ndmod/s4ndmod26-client:<GAME_VERSION>` and no server image is pushed, so promoting a website change does not restart the game server. When you add a file the game stages `COPY`, add its path to `game-version.sh`.
- The plan for the full server/website split (server agent, per-server pk3 downloads) is `~/.claude/plans/i-want-to-start-serialized-lovelace.md`.

## Server agent (`s4nd-agent`)
The server image's entrypoint (`infra/web/status-api/cmd/s4nd-agent`, package `agent`): prepares the mod folder (copies the image's qagame + pk3, removes old pk3s, writes `latest.txt`, links retail paks), runs `iowolfded` in its own process group and restarts it with backoff, and serves on `AGENT_HTTP_ADDR` (`:27970`): `GET /v1/info` (server id, game version, `engine_api`, pk3 name/size/sha256), `/v1/status`, `/v1/replays[/{name}]`, `/v1/stats[/{name}]` (Range supported), `/dl/s4ndmod26/{pk3|latest.txt}`, and the browser bridge at `/ws` (also `/` with an Upgrade header). Settings are env vars, see `agent/config.go`.
- With `SERVER_CFG_TEMPLATE` set it fills `RCON_PASSWORD_PLACEHOLDER` / `SV_DLURL_PLACEHOLDER` / `SV_PURE_PLACEHOLDER` from `RCON_PASSWORD` / `SV_DLURL` / `SV_PURE` (and `SV_DEVMAP=1` turns `map` into `devmap`) into `main/agent_server.cfg`; without it `server.cfg` runs as before.
- The server folder (`/rtcw/s4ndmod26`, one volume) holds everything a server keeps: `server.cfg`, replays, stats and the identity key (`.agent/identity.pem`, `AGENT_STATE_DIR` overrides). The web pod still mounts that folder and serves it under `/downloads/`, so nginx answers 404 for any dot-path and 403 for `.cfg`; write nothing else secret there (generated config goes to `main/agent_server.cfg`).
- A folder with no `server.cfg` gets a starter one from `infra/server/server.cfg.default` (random rcon unless `RCON_PASSWORD`; `sv_dlURL` from `SV_DLURL`, else `AGENT_PUBLIC_URL/dl`); an existing one, even empty, is never touched.
- Self-hosting (docker compose, the main way others will run servers): `selfhost/` (compose with an optional `https` Caddy profile, `.env.example`, README). Browser play on a self-hosted server needs the host's own HTTPS; there is no relay through s4ndmod.com.
- Its sources are game paths in `tools/ci/game-version.sh` and are built in the `agent-builder` stage from only `agent/`, `q3status/`, `cmd/s4nd-agent/`; if the agent starts importing another package, add it to both.
- Tests: `go test -race ./agent ./q3status` (seconds; the bridge test runs against a fake UDP server).

## Join tickets (site side: `status-api/ticket`)
`POST /api/tickets {"server": "<id or the address you connect to>"}` with `Authorization: Bearer ...` returns `{ticket, server_id, account, expires}`; `GET /api/tickets/key` returns the site's Ed25519 public key (what servers verify with). A ticket is 95 fixed bytes (version, account id, server id = the 10 bytes behind the agent's 16-letter id, expiry, random id, signature over `"s4nd-ticket-v1"` + the first 31 bytes), 127 characters of base64url; layout in `ticket.go`, which the game module's C reader must match. Bearer token: bound to one server id, at most 5 minutes (90 s default), single use (a server remembers the id until expiry), 30 per minute per account. Off unless `TICKET_SIGNING_KEY` (32-byte seed, base64; `openssl rand -base64 32`), `TICKET_SERVERS` (`id=addr;addr,id=addr`, the registry's stand-in) and, **until real accounts exist, a dev-only `TEST_ACCOUNT_TOKEN`** (24+ chars; `TEST_ACCOUNT_ID` 1, `TEST_ACCOUNT_NAME` testplayer) are set; with a missing piece it logs why and stays off. Plan: "Player identity: site-issued join tickets".

### Join tickets: game server side
`mod/src/game/g_ticket.c` (glue), `g_ticket_core.c` (pure C: base64/base32 decoding, ticket verification, the single-use table; no game types so `tools/local/test_ticket.sh` can test it) and `g_ed25519.c` (verify-only Ed25519 in TweetNaCl's structure with its constant tables computed by script, not typed). The player's client sends `s4nd_ticket <ticket>` after it joined (a console `/s4nd_ticket ...` works too: unknown commands are forwarded); a good one sets `sess.accountId` (kept in the session cvar across map changes) and the stats lines get `"account":N` (`0`: none; `stats.Line.Account`). Needs `s4nd_server_id` (a server info variable so it shows in getstatus; s4nd-agent passes `+set s4nd_server_id <its id>`; **not** `CVAR_ROM`: the engine resets a read-only cvar set on the command line to the game's default, which emptied it in the PR #111 preview) and `s4nd_ticket_key` (the site's public key; agent env `TICKET_PUBLIC_KEY`, any base64 form, validated at start and passed to the server **URL-safe**: the engine splits its command line at every unquoted `+`, and a standard base64 key with a `+` reached the server cut in two in the PR #111 preview; rcon can change it): either missing = the server takes no tickets. Refused: bad signature, another server's id, expired (30 s of clock skew allowed), a repeated ticket id, account 0, a second ticket on one connection, more than 3 attempts a map. Clients that send nothing play as before.
- **Wasm qagame**: `iortcw/Makefile` lists the game sources explicitly (`S4ND_GAME_SRCS`, mirrors the Jamfile glob); a new `g_*.c` must be added there too or the browser build fails to link. (`g_sha1.c` is Lua-only and in neither.)
- `tools/local/test_ticket.sh` (go + gcc, seconds): C against Go's `crypto/ed25519` and `ticket.Issue` on thousands of vectors (every single-bit change of signatures, messages, keys and tickets, S+L malleation, expiry edges, wrong server/key), built with ASan + UBSan. `go run ./cmd/ticketvec mint <seed> <account> <server id>` makes a real ticket for trying a server by hand. It also covers the key identity (`bg_identity.c`, `g_auth_core.c`; the glue is `g_auth.c`: `s4nd_challenge` out, `s4nd_auth <key> <sig> <address>` in, `sess.keyId`, `"pid"` in stats lines), but not the glue itself: that needs a live server (agent passes `s4nd_auth_key` and, from `AGENT_PUBLIC_NAMES`, `s4nd_public_names`). Not tested: a 32-bit build (no multilib here); the code only uses `long long`.

## Inspecting archives without the game
Archive v8: 2668-byte header, then chunks (24-byte header: startTime, endTime, frameCount, eventCount, uncompressed, compressed sizes + zlib payload).  Payload = frameCount, eventCount, then per frame `serverTime, sampleCount, samples[sampleSize]`, then events.  In a sample the `entityState_t` starts at byte 72 (`eType` +4, `eventSequence` +192, `events[4]` +196, `weapon` +232); `viewangles` at 384.  `status-api/replay/parser.go` is the reference.  Event enum values: see `bg_public.h` (`EV_FIRE_WEAPON` = 40, `ET_MISSILE` = 3, weapon ids `WP_*`).

## Optional text font (cg_s4ndfont)
- `mod/src/cgame/cg_s4ndfont.c`: `cg_s4ndfont 0|1|2` (game font / Courier Prime Bold / DejaVu Sans Mono Bold) draws the charset text (scoreboard, kill feed, chat, titles) with a baked font; `cg_s4ndfontSize` and `cg_s4ndfontSpace` tune it.  It hooks `CG_DrawStringExt`/`CG_DrawStringExt2` in `cg_drawtools.c`.
- Anything that centres, right-aligns or counts characters with `charWidth * strlen` must use `CG_S4ndFont_StrWidth()` / `CG_S4ndFont_Advance()` instead, or it sits off when the font is on (they return the old width when it is off).
- The engine looks baked fonts up by **point size only** (`fonts/fontImage_<size>.dat`), so the size is the font's identity: 30 Courier Prime Bold, 28 DejaVu Sans Mono Bold.  The menus use 12, 16, 17, 20, 24 - do not reuse them.  A stock engine has 6 font slots (`MAX_FONTS`, raised to 16 in our renderer) and the menus take 5, so only the selected font is registered.
- Bake a font with `tools/local/bakefont.py <ttf> <size> mod/main` (needs Pillow); `mod/main/fonts` is packed into the pk3 by the Dockerfile and `tools/local/build_wasm.sh`.  Only add fonts that are free to redistribute (no Microsoft fonts).

## Client demo pipeline (`status-api/demo`)
`demoinspect -replay f.dm_60` converts one demo, `demoinspect -merge a.dm_60 b.dm_60 ...` merges the POVs of one game. Both print what `replay.Analyze` makes of the result. What a client demo does and does not carry, learned against the OSP scoreboards inside the demos (the `sc` commands: Kll/Dth/Sui/TK/DG/DR/TD per player; each round's board is cumulative for the map):
- **Kills** are `EV_OBITUARY` temp entities (victim `otherEntityNum`, killer `otherEntityNum2`, means of death `eventParm`). Entity-event numbers differ per protocol (dm_60 eType 125, dm_59 123, dm_57 121), so `detectObituary` finds the type from the data. Only count them while OSP's `gamestate` (in `cs[36]`) is 0; warm-up deaths are not scored. The same obituary seen by two demos is merged within 500 ms (same killer and victim). About 1-2% of kills still exceed the scoreboard; the ones examined were lieutenant artillery kills the scoreboard does not credit.
- **The playerState belongs to `ps.clientNum`**: the recorder while alive, but the player they follow after dying. It gives exact health at full rate. The recorder's own entity is not in the snapshot. Never stamp it on the recorder's slot.
- **`tinfo`** (about 1/s, same format in dm_57/59/60): `tinfo ident identHealth n` then client, location, health, powerups, class per teammate. Health and class of a recorder's whole team. Class is 0 soldier, 1 medic, 2 engineer, 3 lieutenant (checked by `TestClassNumbering`: artillery/airstrike killers are all class 3, rocket and sniper killers class 0). Means-of-death numbers in the demos are the mod's `meansOfDeath_t` (15-18 pistols/SMGs, 21 sniper, 46 airstrike, 49 artillery, 56 suicide).
- **Teams** change during a demo (sides swap at the round restart); use `teamTimeline`, not the final roster. `entityState.teamNum` is not the team.
- **Damage received** = health lost down to zero. Counting overkill or shots at a downed player overshoots the scoreboard's DR by 10-40%.
- **Damage given**: bullet hits (`EV_BULLET_HIT_FLESH`: victim `eventParm`, shooter `otherEntityNum`; also detected from the data) and missiles (thrower = player within 150 units of the launch point at launch time, using merged positions). Dynamite, airstrikes, artillery, fire and melee are not attributed yet.
- **What the viewer's other layers need** (the demo has no recorder, so each is rebuilt): missiles and dropped packs are entity samples whose positions are trajectories (`traj.go`: base + velocity from `trTime`, gravity for grenades; steps between frames are 40-130 units, `TestMissileTrajectories`), kept by the parser only for `ET_MISSILE` and for items with `otherEntityNum2` set (dropped by a player; the map's own are not kept). Other players' firing comes from `EF_FIRING` (0x100) in their entity flags, mapped to weapon state 6, which is what `replay.BuildShots` reads; damage events get the victim's chest as their hit position. Revives are not announced to everyone: a player down and then up within 45 s and 200 units of where they fell is a revive, the reviver the nearest medic (`TestRevivesVsMessages` checks it against the "You have been revived by" messages recorders get). Dropped packs are off by default in `paths.html` but on in `demos/view.html`.
- Time outside live play (warm-up, intermission, scoreboard) is cut from the replay: during intermission every client is moved to one spot, which shows as everyone flying to the same place. See `demo/rounds.go`.
- Tests: `TestKillEventsVsScoreboard`, `TestDamageReceivedVsScoreboard`, `TestDamageGivenVsScoreboard`, `TestMergeSamples`; run them under the memory cap above.

Uploads are stored under the owner name `acct:<id>`.
- Code: `status-api/demomatches.go` (API), `demopaths.go` (merged output for the viewer), `demostore/` (keys, blob store, Postgres: matches `demo_matches`, files `demo_files`, per-owner claims `demo_uploads`; own migrations and `demo_schema_migrations` table). Demos are stored by sha256 (`raw/ab/<sha>`): the same file uploaded twice is one blob with two claims, and the blob and a match with no demos left are deleted when the last claim is removed. The merged replay is kept gzipped (`paths/<match>-v<N>.json.gz`) for the match's version, which changes when its demos do. Blobs are behind the `blobstore.Blobs` interface (package `status-api/blobstore`, shared so game replays can use it later): a folder by default (`USERDEMO_DIR`, default `/userdemos` from `gamedata/userdemos`, git-ignored), or an S3 bucket (Garage, MinIO, AWS) when `USERDEMO_S3_BUCKET` is set, with `USERDEMO_S3_ENDPOINT` (host:port, no scheme), `_ACCESS_KEY`, `_SECRET_KEY`, optional `_REGION` (default `garage`), `_INSECURE=1` (plain HTTP in-cluster), `_KEY_PREFIX`. Setting both a bucket and `USERDEMO_DIR` refuses to start. `blobstore.FromEnv(ctx, prefix, defaultDir)` reads the same set under any prefix. Upload limits are per key (`USERDEMO_UPLOADS_PER_HOUR`, 60) and per IP (twice that, shared by everyone behind an address); every answer from `POST /upload`, and `GET /mine`, carries `rate` (`limit`, `used`, `remaining`, `reset_secs`, `by`) and the uploader pages show it and stop sending once none are left. A match whose raw demo files are gone from the store (storage replaced while the database was kept) answers 410 with a reason instead of merging without them. S3 is tested against an in-memory fake (`blobstore_test.go`), not a real Garage.
- API: public `GET /api/demos/matches`, `/matches/{id}`, `/matches/{id}/paths`; keyed `POST /api/demos/upload?name=x.dm_60` (raw body), `GET /api/demos/mine`, `DELETE /api/demos/files/{id}`; series (below). Also `USERDEMO_MAX_FILE_MB` (40), `USERDEMO_MAX_DEMOS` per match (60), `USERDEMO_UPLOADS_PER_HOUR` per key (60). nginx sets `X-Real-IP` for the rate limits (`/api/demos` location, which also raises the body limit to 40 MB).
- **Series** link matches in order (the games of a final): `demo_series` plus `demo_matches.series_id/series_pos` (migration 002); public `GET /api/demos/series`, `/series/{id}`, and `series` (pos, prev, next) in `/matches/{id}`; keyed `POST /api/demos/series`, `PUT /series/{id}` (`{name, matches: [ids in order]}`), `DELETE /series/{id}`. A key can only link matches it has uploaded a demo of; any key with a demo in one of a series' matches (or the key that made it) can rename, reorder or dissolve it, and adding a match takes a demo of that match; a series with no matches is deleted, and a match folded into another by a bridging demo passes its series on. Page: `demos/series.html`. In the viewer, play stops on the last frame of each round but the last (Play goes on to the next round) and at the end of the game offers the next game of the series. `Compressor.Replay` leaves out the frame stamped with the instant a round ends: it is the first one after the server moved everyone to the intermission spot.
- **Stats** (`demo/stats.go`, `GET /api/demos/matches/{id}/stats`, shown on `match.html`) are per round (1 of 2, 2 of 2): kills, deaths, suicides, team kills, objective steals/deliveries and carry time, team and class, and the round's clock and objective events. They are part of the merged output (`stats` in the paths JSON), so the endpoint reads the kept merge and rebuilds output kept before stats existed. Only what was checked against the OSP scoreboards or the game's own messages is counted: **not** damage, accuracy or revives (revive precision is about 80% where checkable; they stay in the viewer's feed only). `stats.ticks` lists every count with the moment it happened (`t_ms` from the start of the replay, like the feed); `view.html` adds them up to the playhead in the Stats table under the replay ("Match so far" / "This round"), with carry time from the carries, so the figures count as the match plays. Merged output kept before ticks existed shows no table.
- **Names**: `demo_matches.name` (migration 003); `PUT /api/demos/matches/{id}` `{name}` by any key with a demo in the match (empty clears; does not bump the version, so the merged output is kept). **Games**: a long demo (a spectator's) holds several games, so `demo.Round` has `Game` (a round numbered no higher than the one before starts a new game) and rounds under 5 s are dropped (the phase flickers to "playing" at each restart). Stats and the viewer label rounds "Game g · Round n of m" when there is more than one game. **Long demos are split by game**: `demo.Games` cuts a demo that spans two or more games (found from the rounds; 15 s of padding, neighbours meet at the middle of the gap) and `demo.Clip` makes the piece (earlier `cs` commands folded into the initial configstrings, so the phase and clock are right). A split demo is one stored file and one `demo_files` row per game (migration 004: `segment`, `window_from_ms`, `window_to_ms`, unique on `(sha256, segment)`), each placed in the match of its game; `loadDemo` clips a segment row's blob to its window. The upload answers `status: split` with `games` and, when it could, `series_id` (the games are linked in a series, or an existing series holding only these games is updated). Removing one game's upload removes that row only; the file goes with the last row (`Removal.FileGone`). Tested on QCon02 (spectator demo: 3 games; set-spanning player demos split too) and on a 73-minute dm_57 pair (5 games each), in either upload order (`TestDemoSplitsALongDemo`, `TestGamesSplit`).
- A new upload is only parsed against demos of matches that could be the same game (same map, overlapping server time, same `sv_serverid` for two players' demos); an already-stored file is not parsed at all. One parse/merge job runs at a time; `demo.MergeStream` loads demos one at a time.
- Run it locally without Docker: a Postgres (`tools/local/pgrun` starts a throwaway one and exports `STATS_TEST_DSN`), `status-api` started with `STATUS_API_PORT=18080 REPLAY_DIR=<empty dir> USERDEMO_UPLOAD_ENABLED=1 USERDEMO_KEYS_FILE=<file> USERDEMO_DIR=<dir> DATABASE_URL=<dsn>` under the memory cap, and `infra/web/nginx/html` served with `/api` proxied to it (nginx does this in production). Without the game's pk3 the map mesh 404s and the viewer shows a grid.
- Tests: `tools/local/demos_test.sh` (starts a throwaway Postgres; set `DEMO_SAMPLES` for the real-demo flow `TestDemoMatchesFlow`, and run under the memory cap). The `demo` package's sample tests need no database.

## Gotchas
- **Line endings:** several mod files are CRLF (some mixed), e.g. `cg_weapons.c`, `cg_local.h`.  Edit them with the Edit tool or byte-level scripts; a Python text-mode read/write rewrites every line ending and buries the change in a whole-file diff.  Check `git diff --stat` after editing.
- `node` is not on PATH in the dev shell; use the emsdk copy: `export PATH=$HOME/.local/share/emsdk/node/24.19.0_64bit/bin:$PATH`.
- Headless swiftshader screenshots take ~1.3 s each and lag the game; to catch a fast event (a rocket flight is ~0.3 s) set `g_replayDebug 1`, watch the console for `frame N serverTime T`, and set `timescale 0.1-0.3` (`Module.ccall('wasm_set_cvar',null,['string','string'],['timescale','0.2'])`) when T nears the event.  Temporary `CG_Printf` prints in cgame show up in the page console.
- Missile explosions are not in archives: `G_ExplodeMissile` keeps the blast in the entity event ring and frees it in 300 ms, so playback rebuilds blasts when a missile stops being recorded (`G_ReplayExplodeVanished`).
- Replay entities are forced `inuse` over map slots; temp entities (`G_TempEntity`) are how playback fires one-shot effects (obituaries, blood, blasts).
- Commit messages/PRs: follow the attribution lines in the session instructions.

## Account link (`/link CODE`)
A player's key can be tied to a site account.  The account holder `POST /api/link/codes` (the dev test token logs in; `Authorization: Bearer ...`) and gets a code like `ABCD-EFGH`, valid 10 minutes, one use.  In game they type `/link ABCD-EFGH` (with the slash: without it the console sends chat).  qagame (`G_Link_Command`, needs an identified player and `s4nd_link 1`) appends `link <key> <CODE>` to `link.log` in the mod folder; the agent (`agent/linkrelay.go`, set `AGENT_LINK_URL=<site>/api/link/claim`) signs it with the server key and posts it; the site (`link` package, needs the ticket env: `TICKET_SIGNING_KEY`, `TICKET_SERVERS` listing the agent's server id, `TEST_ACCOUNT_TOKEN`) parks the key as pending until `POST /api/link/confirm {"key":...}`.  `LINK_STATE_FILE` keeps the data across site restarts.  Tested by `go test ./link ./agent`; run live locally the same way as the identity test above.

## Accounts (`status-api/accounts`, step 1)
Local accounts in Postgres (own migrations, `account_schema_migrations`): username, email, argon2id password, sessions (only a SHA-256 of the token is stored; cookie `s4nd_session`, HttpOnly, SameSite=Lax, or `Authorization: Bearer` for scripts), and `account_permissions` (`demo_upload`, `host_server`, `admin`).  On with `ACCOUNTS_ENABLED=1` + `DATABASE_URL`; when on it is the login for tickets and `/link` instead of `TEST_ACCOUNT_TOKEN`.  API: `POST /api/account/register|login|logout|password`, `GET|DELETE /api/account`, admin `GET /api/admin/accounts?q=`, `PUT|DELETE /api/admin/accounts/{id}/permissions/{perm}`; bodies must be `application/json`.  Rules: a new account has no permissions; **`Account.Has(perm)` is false until the email is verified** (the mail step is not built yet; `accountsctl verify <user>` stands in), so anything gated on a permission must use `Has`.  The first admin: `DATABASE_URL=... go run ./cmd/accountsctl grant <user> admin` (+ `verify`).  Login is throttled per (ip, user) and per ip.  Tests: `tools/local/accounts_test.sh` (throwaway Postgres).  Planned next: email verification and reset, redeeming an old demo-upload key for `demo_upload` (and taking over that label's uploads), server registration, the account page, stats under an account.

**Accounts, step 2** (same package): `POST /api/account/verify|verify/resend|reset|reset/confirm|demo-key`.  Mail goes through `accounts.Mailer`: only `LogMailer` (default), `OutboxMailer` (`ACCOUNTS_MAIL_OUTBOX=<dir>`, one file per mail) and a test `Capture` exist; set `ACCOUNTS_PUBLIC_URL` for the links (`/account/#verify=` and `#reset=`, in the fragment so tokens stay out of logs).  A reset also confirms the address and ends every session.  **Redeeming an old demo key** (`demo-key`) ties the key's label to the account (one key, one account), grants `demo_upload` and calls `demostore.AdoptOwner` so the label's uploads and series become the account's (`acct:<id>`); afterwards the key only works while the account holds `demo_upload` with a confirmed email.  `demoService.uploader` (demomatches.go) is where uploads are authorised: old key, redeemed key, or a logged-in account with `demo_upload`.  Page: `infra/web/nginx/html/account/` (sign in/up, reset, confirm, demo key, `/link` keys, password, delete, admin).  nginx `/api/` now sets `X-Real-IP` (the login throttles need it).  Local live check: run `status-api` under `tools/local/pgrun` with `ACCOUNTS_ENABLED=1 DATABASE_URL=$STATS_TEST_DSN ACCOUNTS_MAIL_OUTBOX=...`, serve `infra/web/nginx/html` with `/api` proxied, drive `/account/` with playwright.

**Admin area and paging.**  The admin tools are their own area, `/admin/` (`nginx/html/admin/`: `admin.js` has the shared helpers and `A.pager`, `index.html` registers sections with `A.section(id, title, render)`; only Accounts exists, servers and demos get their own section there).  It is for accounts with `admin` and a confirmed email; the account page only links to it.  Long lists are paged on the server: `GET /api/admin/accounts?q=&page=&per=` (per at most 100) answers `{accounts, total, page, per}`; the demo lists take `limit`/`offset` (`/matches`, `/series`, and `/mine?limit=&offset=` which then also gives `uploads_total`; without `limit`, `/mine` still returns everything because `series.html` and `match.html` need all of it).  Pagers are on the demo index (matches and series) and the upload page.

**Admin delete, suspend and the audit log.**  `DELETE /api/admin/accounts/{id}` (`{purge_uploads}`; removes the account like a self-delete, frees its redeemed demo key, and with `purge_uploads` removes what it uploaded through `demoService.purgeOwner`), `POST .../suspend {reason}` and `.../unsuspend`, `GET /api/admin/audit`.  A suspended account has its sessions ended, cannot log in (the refusal is shown only after a correct password), and `Account.Has` is false for it, so uploads, tickets and `/link` stop too.  An admin cannot delete or suspend themselves or the last active admin (permission, confirmed email, not suspended); the self-delete on the account page has the same last-admin guard.  `account_audit` (migration 003) records grant, revoke, suspend, unsuspend and delete with the names copied in so entries outlive the accounts; the admin page has a paged Log section.  Not audited: grants made with `accountsctl`.

At 720px the admin rows stack and the section menu becomes a tab bar; the account page goes full width at 640px. **Server registry** (`status-api/servers`, `probe`, agent `registration.go`; design in the plan's "Server registration"): public servers only, probed from outside over UDP and over `wss://` with a certificate browsers accept (the WSS probe sends a status query through the agent's bridge).  Flow: a `host_server` account asks for a token (`POST /api/servers/tokens`, shown once, `AGENT_REGISTRATION_TOKEN=...`); the agent (`AGENT_REGISTRATION_URL`, `AGENT_PUBLIC_NAMES` first entry = game host:port, `AGENT_PUBLIC_URL` https or `AGENT_PUBLIC_WSS`) sends signed claims (`POST /api/servers/claim`) every 2 min while refused and every 10 min once accepted; a refused claim keeps the token, answers 422 with which probe failed, and records it on the token (shown on the account page).  Accepted = pending; an admin approves (it re-probes, so an unreachable server cannot be approved); `ProbeAll` runs every 3 min (`SERVERS_PROBE_MINUTES`) and a server is listed (`GET /api/servers?kind=official|community`, public, paged, official first) only while both probes pass.  Tickets and `/link` accept approved registry servers next to `TICKET_SERVERS`.  `probe` refuses non-public addresses (checked after name lookup and dialled by the checked IP), ports other than 443 and 1024-65535, and non-`wss`.  Limits: 5 servers+tokens per account by default (`SERVERS_MAX_PER_ACCOUNT`), and an admin can set another number for one account (`PUT /api/admin/accounts/{id}/server-limit`, `{"limit": n}` or null for the default; the "Server limit" button on a host's row in `/admin/`; table `server_limits`; audit action `server_limit`); an address can be registered once; admin actions go to the audit log.  Admin: `/admin/#servers` (approve, block, unblock, mark official = not probed, delete, add an official server by public key).  Local testing needs `SERVERS_DEV=1` (probe loopback, `SERVERS_PROBE_SECONDS`, `SERVERS_DEV_CA=<pem>` to trust a test CA); never in production.  **Joining from the browser:** the Join buttons link to `/play/?server=<server_id>`; `wasm/shell.html` (`communityBootInfo`, synchronous XHR) asks `GET /api/servers/<id>` (only a *listed* server answers; 404 otherwise), then uses its `wss_url` as the WebSocket endpoint and `+connect <game_addr>`.  The agent's claim carries the mod pk3 name (`pk3`, stored in `servers.pk3`); if it differs from the site's `/downloads/s4ndmod26/latest.txt` the page refuses with a message (the browser client plays with the site's own copy of the mod; fetching the server's pk3 is the later "mod from the server you join" step).  An unusable `?server=` sets `Module.noInitialRun` and shows the reason, never falling back to the official server.  Checked headless with a fake registry (`~/.cache/s4ndmod26-wasm/play` from `tools/local/build_wasm.sh`): the WebSocket url and `+connect` are right, bad/old/missing links start nothing.  **Decided (2026-11-13):** hosts bring their own domain and certificate; free random names are optional and later (see the plan).  **Not built yet:** the browser client using a registered server's address, purging a deleted server's stats.
