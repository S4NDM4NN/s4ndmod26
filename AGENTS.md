# AGENTS.md

Notes for AI agents (and people) working in this repo.  Keep this file current: when you learn a build/test step the hard way, add it here.

## Layout
- `mod/src/game` (qagame), `mod/src/cgame`, `mod/src/ui` — the mod.  Replay recorder/playback is `mod/src/game/g_replay.c`; its client side lives in `cgame` (`cg_servercmds.c` `replay_phase`, `cg_draw.c`, `cg_view.c`).
- `iortcw/` — engine, `wasm/` — browser client glue, `omnibot/` — bots, `infra/web/` — nginx pages + Go `status-api` (parses `.rpl` archives in `status-api/replay/parser.go`).
- Replay archives (`.rpl`, format v8) + sidecar `.txt` live in `gamedata/s4ndmod26/replays/` on a server and under `/downloads/s4ndmod26/replays/` on the web host.

## Quick compile check (seconds)
Syntax-check a changed mod file without a full build:
```bash
cd mod/src && gcc -fsyntax-only -w -DGAMEDLL -DCGAMEDLL -I game -I cgame -I ../../third_party/zlib game/g_replay.c
```

## Official builds (Docker)
`make build` / `make populate` (game modules into `gamedata/`), `make wasm-build` then `make wasm-deploy` (browser client).  Docker is not always installed in the dev shell (it isn't in the WSL session used so far) — use the local wasm build below.

## Game and website versions (separate)
- `GAME_VERSION` (`tools/ci/game-version.sh`: `v<date>-<sha>` of the last commit touching the game paths listed there) tags the server image `s4ndmod26` and the client-files image `s4ndmod26-client`, and is the Dockerfile's `VERSION` (pk3 name, `MOD_BUILD_VERSION`). The website image `s4ndmod26-web` is tagged with this commit's version (`WEB_VERSION`, written to `version.txt`); `client-version.txt` holds the game version and is what the launcher manifest reports. The launcher is NOT a game path (changed 2026-11-14): its binaries and signatures are added by the `web` stage of the Dockerfile (`COPY --from=launcher-builder`), so a launcher or website change reuses the game images and only builds the web image; CI signs and checks the launcher on the web image.
- CI rebuilds the game only when `s4ndmod26:<GAME_VERSION>` and `s4ndmod26-client:<GAME_VERSION>` are not in the registry yet; otherwise the web stage is built with `--build-arg CLIENT_IMAGE=repo.s4ndmod.com/s4ndmod/s4ndmod26-client:<GAME_VERSION>` and no server image is pushed, so promoting a website change does not restart the game server. When you add a file the game stages `COPY`, add its path to `game-version.sh`.
- The plan for the full server/website split (server agent, per-server pk3 downloads) is `~/.claude/plans/i-want-to-start-serialized-lovelace.md`.

## Server agent (`s4nd-agent`)
The server image's entrypoint (`infra/web/status-api/cmd/s4nd-agent`, package `agent`): prepares the mod folder (copies the image's qagame + pk3, removes old pk3s, writes `latest.txt`, links retail paks), runs `iowolfded` in its own process group and restarts it with backoff, and serves on `AGENT_HTTP_ADDR` (`:27970`): `GET /v1/info` (server id, game version, `engine_api`, pk3 name/size/sha256), `/v1/status`, `/v1/replays[/{name}]`, `/v1/stats[/{name}]` (Range supported), `/dl/s4ndmod26/{pk3|latest.txt}`, and the browser bridge at `/ws` (also `/` with an Upgrade header). Settings are env vars, see `agent/config.go`.
- With `SERVER_CFG_TEMPLATE` set it fills `RCON_PASSWORD_PLACEHOLDER` / `SV_DLURL_PLACEHOLDER` / `SV_PURE_PLACEHOLDER` from `RCON_PASSWORD` / `SV_DLURL` / `SV_PURE` (and `SV_DEVMAP=1` turns `map` into `devmap`) into `main/agent_server.cfg`; without it `server.cfg` runs as before.
- The server folder (`/rtcw/s4ndmod26`, one volume) holds everything a server keeps: `server.cfg`, replays, stats and the identity key (`.agent/identity.pem`, `AGENT_STATE_DIR` overrides). The web pod still mounts that folder and serves it under `/downloads/`, so nginx answers 404 for any dot-path and 403 for `.cfg`; write nothing else secret there (generated config goes to `main/agent_server.cfg`).
- A folder with no `server.cfg` gets a starter one from `infra/server/server.cfg.default` (random rcon unless `RCON_PASSWORD`; `sv_dlURL` from `SV_DLURL`, else `AGENT_PUBLIC_URL/dl`); an existing one, even empty, is never touched.
- Self-hosting (docker compose, the main way others will run servers): `selfhost/` (compose with an optional `https` Caddy profile, `.env.example`, README). Browser play on a self-hosted server needs the host's own HTTPS; there is no relay through s4ndmod.com.
- Its sources are game paths in `tools/ci/game-version.sh` and are built in the `agent-builder` stage from only `agent/`, `q3status/`, `cmd/s4nd-agent/`; if the agent starts importing another package, add it to both.
- Tests: `go test -race ./agent ./q3status` (seconds; the bridge test runs against a fake UDP server).

## Join tickets (site side: `status-api/ticket`)
`POST /api/tickets {"server": "<id or the address you connect to>"}` with `Authorization: Bearer ...` returns `{ticket, server_id, account, expires}`; `GET /api/tickets/key` returns the site's Ed25519 public key (what servers verify with). A ticket is 95 fixed bytes (version, account id, server id = the 10 bytes behind the agent's 16-letter id, expiry, random id, signature over `"s4nd-ticket-v1"` + the first 31 bytes), 127 characters of base64url; layout in `ticket.go`, which the game module's C reader must match. Bearer token: bound to one server id, at most 5 minutes (90 s default), single use (a server remembers the id until expiry), 30 per minute per account. Off unless `TICKET_SIGNING_KEY` (32-byte seed, base64; `openssl rand -base64 32`), `TICKET_SERVERS` (`id=addr;addr,id=addr`, the registry's stand-in) and, **until real accounts exist, a dev-only `TEST_ACCOUNT_TOKEN`** (24+ chars; `TEST_ACCOUNT_ID` 1, `TEST_ACCOUNT_NAME` testplayer) are set; with a missing piece it logs why and stays off. Plan: "Player identity: site-issued join tickets".

### Join tickets: game server side
`mod/src/game/g_ticket.c` (glue), `g_ticket_core.c` (pure C: base64/base32 decoding, ticket verification, the single-use table; no game types so `tools/local/test_ticket.sh` can test it) and `g_ed25519.c` (verify-only Ed25519 in TweetNaCl's structure with its constant tables computed by script, not typed). The player's client sends `s4nd_ticket <ticket>` after it joined (a console `/s4nd_ticket ...` works too: unknown commands are forwarded); a good one sets `sess.accountId` (kept in the session cvar across map changes) and the stats lines get `"account":N` (`0`: none; `stats.Line.Account`). Needs `s4nd_server_id` (a server info variable so it shows in getstatus; s4nd-agent passes `+set s4nd_server_id <its id>`; **not** `CVAR_ROM`: the engine resets a read-only cvar set on the command line to the game's default, which emptied it in the PR #111 preview) and `s4nd_ticket_key` (the site's public key; agent env `TICKET_PUBLIC_KEY`, any base64 form, validated at start and passed to the server **URL-safe**: the engine splits its command line at every unquoted `+`, and a standard base64 key with a `+` reached the server cut in two in the PR #111 preview; rcon can change it): either missing = the server takes no tickets. Refused: bad signature, another server's id, expired (30 s of clock skew allowed), a repeated ticket id, account 0, a second ticket on one connection, more than 3 attempts a map. Clients that send nothing play as before.
- **Wasm qagame**: `iortcw/Makefile` lists the game sources explicitly (`S4ND_GAME_SRCS`, mirrors the Jamfile glob); a new `g_*.c` must be added there too or the browser build fails to link. (`g_sha1.c` is Lua-only and in neither.)
- `tools/local/test_infovalidate.sh` (gcc, seconds): `Info_Validate` in the game module's and the engine's `q_shared.c` rejects quotes, semicolons and control characters (newline, ESC, DEL; the game turns such a userinfo into the name `badinfo`) but allows bytes above 0x7f so accented names still work. This is stricter than before but looser than ioquake3 `a6f949c8`, which also rejects every non-ASCII byte (`Q_isprint`) and would rename players like `Müller` to `badinfo`.
- `tools/local/test_bans.sh <iowolfded> <dir with main/ + s4ndmod26/>` (real server, about 20 s): bans saved by `banaddr` are loaded again when `server.cfg` runs `rehashbans` before the first map (the command used to return unless a map was running; ioquake3 `56f9f94e`). Bans are written to `fs_homepath`, so give it its own. Put `rehashbans` in `server.cfg` if you want bans to survive a restart.
- `tools/local/test_msg.sh` (gcc, seconds): `MSG_WriteBits` must set the overflow flag when the bit count reaches the buffer size (the message length is `(bit >> 3) + 1`, one more than the buffer holds); exactly-sized buffers under ASan + UBSan; fails on the old `>` checks. Fix from ioquake3 `1e309787`.
- `tools/local/test_dropclient.sh <iowolfded> <dir with main/ + s4ndmod26/qagame.mp.x86_64.so>` (real server, about 20 s, needs the retail paks and a built engine/game module): a silent UDP client (`tools/local/dropclient/`: connects, never acknowledges) gets `MAX_RELIABLE_COMMANDS` `say` lines queued by `rcon exec`, then is kicked; passes only if the game's disconnect hook runs once (`SV_DropClient` recursion fix from ioquake3 `cc18246f`; before it: two). Notes from building it: the netchan header is sequence, qport, checksum (`challenge ^ sequence * challenge`); rcon is rate limited per source, so every command uses a new socket; `say` from the console reaches only clients the engine has primed (it is an engine broadcast), the mod's own chat does not.
- `tools/local/test_huffman.sh` (gcc, seconds): `Huff_Decompress` (the server runs it on unauthenticated `connect` packets, `sv_main.c`) on 200,000 malformed packets in exactly-sized buffers under ASan + UBSan, plus text packets round-tripping through `Huff_Compress`. Fix ported from ioquake3 (#894).
- `tools/local/test_ticket.sh` (go + gcc, seconds): C against Go's `crypto/ed25519` and `ticket.Issue` on thousands of vectors (every single-bit change of signatures, messages, keys and tickets, S+L malleation, expiry edges, wrong server/key), built with ASan + UBSan. `go run ./cmd/ticketvec mint <seed> <account> <server id>` makes a real ticket for trying a server by hand. It also covers the key identity (`bg_identity.c`, `g_auth_core.c`; the glue is `g_auth.c`: `s4nd_challenge` out, `s4nd_auth <key> <sig> <address>` in, `sess.keyId`, `"pid"` in stats lines), but not the glue itself: that needs a live server (agent passes `s4nd_auth_key` and, from `AGENT_PUBLIC_NAMES`, `s4nd_public_names`). Not tested: a 32-bit build (no multilib here); the code only uses `long long`.

## Inspecting archives without the game
Archive v8: 2668-byte header, then chunks (24-byte header: startTime, endTime, frameCount, eventCount, uncompressed, compressed sizes + zlib payload).  Payload = frameCount, eventCount, then per frame `serverTime, sampleCount, samples[sampleSize]`, then events.  In a sample the `entityState_t` starts at byte 72 (`eType` +4, `eventSequence` +192, `events[4]` +196, `weapon` +232); `viewangles` at 384.  `status-api/replay/parser.go` is the reference.  Event enum values: see `bg_public.h` (`EV_FIRE_WEAPON` = 40, `ET_MISSILE` = 3, weapon ids `WP_*`).

## Optional text font (cg_s4ndfont)
- `mod/src/cgame/cg_s4ndfont.c`: `cg_s4ndfont 0|1|2` (game font / Courier Prime Bold / DejaVu Sans Mono Bold) draws the charset text (scoreboard, kill feed, chat, titles) with a baked font; `cg_s4ndfontSize` and `cg_s4ndfontSpace` tune it.  It hooks `CG_DrawStringExt`/`CG_DrawStringExt2` in `cg_drawtools.c`.
- Anything that centres, right-aligns or counts characters with `charWidth * strlen` must use `CG_S4ndFont_StrWidth()` / `CG_S4ndFont_Advance()` instead, or it sits off when the font is on (they return the old width when it is off).
- The engine looks baked fonts up by **point size only** (`fonts/fontImage_<size>.dat`), so the size is the font's identity: 30 Courier Prime Bold, 28 DejaVu Sans Mono Bold.  The menus use 12, 16, 17, 20, 24 - do not reuse them.  A stock engine has 6 font slots (`MAX_FONTS`, raised to 16 in our renderer) and the menus take 5, so only the selected font is registered.
- Bake a font with `tools/local/bakefont.py <ttf> <size> mod/main` (needs Pillow); `mod/main/fonts` is packed into the pk3 by the Dockerfile and `tools/local/build_wasm.sh`.  Only add fonts that are free to redistribute (no Microsoft fonts).

## Client demo pipeline (`status-api/demo`)
`demoinspect -replay f.dm_60` converts one demo, `demoinspect -merge a.dm_60 b.dm_60 ...` merges the POVs of one game. Both print what `replay.Analyze` makes of the result. What a client demo does and does not carry, learned against the OSP scoreboards inside the demos (the `sc` commands: Kll/Dth/Sui/TK/DG/DR/TD per player; each round's board is cumulative for the map):
- **Kills** are `EV_OBITUARY` temp entities (victim `otherEntityNum`, killer `otherEntityNum2`, means of death `eventParm`). Entity-event numbers differ per protocol (dm_60 eType 125, dm_59 123, dm_57 121), so `detectObituary` finds the type from the data. Only count them while OSP's `gamestate` (in `cs[36]`) is 0; warm-up deaths are not scored. The same obituary seen by two demos is merged within 500 ms (same killer and victim). About 1-2% of kills still exceed the scoreboard; the ones examined were lieutenant artillery kills the scoreboard does not credit.
- **The playerState belongs to `ps.clientNum`**: the recorder while alive, but the player they follow after dying. It gives exact health at full rate. The recorder's own entity is not in the snapshot. Never stamp it on the recorder's slot.
- **`tinfo`** (about 1/s, same format in dm_57/59/60): `tinfo ident identHealth n` then client, location, health, powerups, class per teammate. Health and class of a recorder's whole team. Class is 0 soldier, 1 medic, 2 engineer, 3 lieutenant (checked by `TestClassNumbering`: artillery/airstrike killers are all class 3, rocket and sniper killers class 0). Means-of-death numbers in the demos are the mod's `meansOfDeath_t` (15-18 pistols/SMGs, 21 sniper, 46 airstrike, 49 artillery, 56 suicide).
- **Teams** change during a demo (sides swap at the round restart); use `teamTimeline`, not the final roster. `entityState.teamNum` is not the team.
- **Damage received** = health lost down to zero. Counting overkill or shots at a downed player overshoots the scoreboard's DR by 10-40%.
- **Damage given**: bullet hits (`EV_BULLET_HIT_FLESH`: victim `eventParm`, shooter `otherEntityNum`; also detected from the data) and missiles (thrower = player within 150 units of the launch point at launch time, using merged positions). Dynamite, airstrikes, artillery, fire and melee are not attributed yet.
- **What the viewer's other layers need** (the demo has no recorder, so each is rebuilt): missiles and dropped packs are entity samples whose positions are trajectories (`traj.go`: base + velocity from `trTime`, gravity for grenades; steps between frames are 40-130 units, `TestMissileTrajectories`), kept by the parser only for `ET_MISSILE` and for items with `otherEntityNum2` set (dropped by a player; the map's own are not kept). Other players' firing comes from `EF_FIRING` (0x100) in their entity flags, mapped to weapon state 6, which is what `replay.BuildShots` reads; damage events get the victim's chest as their hit position. Revives are not announced to everyone: a player down and then up within 45 s and 200 units of where they fell is a revive, the reviver the nearest medic (`TestRevivesVsMessages` checks it against the "You have been revived by" messages recorders get). Dropped packs are off by default in `paths.html` but on in `demos/view.html`.
- Time outside live play (warm-up, intermission, scoreboard) is cut from the replay: during intermission every client is moved to one spot, which shows as everyone flying to the same place. See `demo/rounds.go`.
- Tests: `TestKillEventsVsScoreboard`, `TestDamageReceivedVsScoreboard`, `TestDamageGivenVsScoreboard`, `TestMergeSamples`; run them under the memory cap above.

Blobs are behind the `blobstore.Blobs` interface (package `status-api/blobstore`, shared so game replays can use it later): a folder by default (`USERDEMO_DIR`, default `/userdemos` from `gamedata/userdemos`, git-ignored), or an S3 bucket (Garage, MinIO, AWS) when `USERDEMO_S3_BUCKET` is set, with `USERDEMO_S3_ENDPOINT` (host:port, no scheme), `_ACCESS_KEY`, `_SECRET_KEY`, optional `_REGION` (default `garage`), `_INSECURE=1` (plain HTTP in-cluster), `_KEY_PREFIX`. Setting both a bucket and `USERDEMO_DIR` refuses to start. `blobstore.FromEnv(ctx, prefix, defaultDir)` reads the same set under any prefix. Upload limits are per key (`USERDEMO_UPLOADS_PER_HOUR`, 60) and per IP (twice that, shared by everyone behind an address); every answer from `POST /upload`, and `GET /mine`, carries `rate` (`limit`, `used`, `remaining`, `reset_secs`, `by`) and the uploader pages show it and stop sending once none are left. A match whose raw demo files are gone from the store (storage replaced while the database was kept) answers 410 with a reason instead of merging without them. S3 is tested against an in-memory fake (`blobstore_test.go`), not a real Garage.

## Gotchas
- **Line endings:** several mod files are CRLF (some mixed), e.g. `cg_weapons.c`, `cg_local.h`.  Edit them with the Edit tool or byte-level scripts; a Python text-mode read/write rewrites every line ending and buries the change in a whole-file diff.  Check `git diff --stat` after editing.
- `node` is not on PATH in the dev shell; use the emsdk copy: `export PATH=$HOME/.local/share/emsdk/node/24.19.0_64bit/bin:$PATH`.
- Headless swiftshader screenshots take ~1.3 s each and lag the game; to catch a fast event (a rocket flight is ~0.3 s) set `g_replayDebug 1`, watch the console for `frame N serverTime T`, and set `timescale 0.1-0.3` (`Module.ccall('wasm_set_cvar',null,['string','string'],['timescale','0.2'])`) when T nears the event.  Temporary `CG_Printf` prints in cgame show up in the page console.
- Missile explosions are not in archives: `G_ExplodeMissile` keeps the blast in the entity event ring and frees it in 300 ms, so playback rebuilds blasts when a missile stops being recorded (`G_ReplayExplodeVanished`).
- Play-of-the-game scoring (`REPLAY_SCORE_*`, summed over a 10 s window per player, a human's total counts double against bots): a kill is 100 (+25 head, +50/+100 for the 2nd/3rd kill in 3 s); a document/flag capture is 300; a spawn-flag capture is 60 and a dynamite plant 25 (were 300 and 50, which made plant-then-run-to-the-bunker-flag beat a double kill). Scores are stored in each archived event and the play of the game is stored in the sidecar, so this only affects games recorded after the change. Re-scoring prod's 95 human games with the new numbers changes the pick in 5.
- A play of the game needs at least one enemy kill in its 10 s window (`G_ReplayWindowKills`, used by the live candidate, `G_ReplayFindBestSelection` and the debug breakdown); an objective-only or bomb-run window can no longer win, even if it scores higher.  A game with no kill by anyone has no play of the game.  Highlights already needed a kill or an objective.  Games recorded before the change keep their stored pick.
- Strike shots when the thrower died before the kills: a play of the game's clip is the thrower's alive run around the last kill, so a thrower who called artillery (or threw a smoke can), died and respawned has a clip that starts AFTER the call. The shot needs the launch event (artillery) or the can's frames (airstrike, up to 9 s back), and a replay server loads only part of the recording, so the shot was silently missing and the clip showed only the kills somewhere else (seen on replays_20261108_012400, mp_beach: launch 11.8 s before the clip). Fixed in `G_ReplayLoadFromFile` (potg loads `REPLAY_LOAD_BEFORE_MSEC` = 20 s before the clip, like a highlight loads 40 s) and `G_ReplayExtendForShots` (stretches the clip back to the call and forward to the shot's end; shared with `G_ReplayTightenSelection`). About 10% of strike barrages on prod (51 of 483 in 96 human games, Nov 2026) had the thrower die between the call and the kills.
- **Dynamite shot** (`REPLAY_STRIKE_DYNAMITE`, appended to the strike enum because archives store the numbers): a dynamite kill (`MOD_DYNAMITE`/`_SPLASH`; all victims of one blast share a timestamp and merge into one shot) becomes a highlight shot like artillery, but indoors a far pan-out does not work, so `G_ReplayChooseDynamiteCamera` picks ONE fixed camera: it needs the charge (`inflictorOrigin` of the kill event; the plant event's origin is recorded as 0) and every victim (kill spot plus where they were 0.7 s and 1.4 s earlier, weighted) inside a real frustum test with line of sight, then prefers open space (nine rays), eye height and about 230 units away (340 and never closer than 220 when there is one victim: nothing to frame, and gibs fill the lens). The shot opens 1.5 s before the blast, or at the planter's death when they died up to 6 s before it (playback would otherwise stop at the death), and holds 3.5 s after. The planter's own view is kept as an inset when they were fighting in the 4 s before (`G_ReplayActorEngaged`), else it cuts away; `g_replayDynamiteView` -1 auto, 0 always cut away, 1 always inset. Playback loads 4 s of margin (`REPLAY_LOAD_MARGIN_MSEC`) and stretches the clip to cover the shot. A lit charge's `effect1Time` is a server time from the recorded match, so `G_ReplayApplySampleToEntity` shifts it into playback time or the light strobes. Applies to old recordings too: shots are worked out from the `.rpl` at playback.  Local shots of this: `g_replayDebug 1` prints `dynamite camera ...`.  Tested on mp_castle, mp_base (a window shot: the camera looks in through the observation window) and mp_village.
- Artillery/airstrike inset: the player's view stays as the inset only if they were shooting (`G_ReplayActorShooting`: a hit or kill of theirs that is not the strike's own, or the fire button held on a weapon other than binoculars/smoke can, from 3.5 s before the last kill to 0.5 s after); otherwise the strike goes full screen. `g_replayStrikeView` -1 auto, 0 always full screen, 1 always inset. Most play-of-the-game strikes on prod are of the second kind (23 of 29 on mp_beach in Nov 2026).
- Retention on prod (gitops overlay env on the web pod): `REPLAY_BOT_ONLY_MAX_AGE_DAYS=1`, `REPLAY_MAX_AGE_DAYS=30`.
- Replay entities are forced `inuse` over map slots; temp entities (`G_TempEntity`) are how playback fires one-shot effects (obituaries, blood, blasts).
- Commit messages/PRs: follow the attribution lines in the session instructions.

**Server registry** (`status-api/servers`, `probe`, agent `registration.go`; design in the plan's "Server registration"): public servers only, probed from outside over UDP and over `wss://` with a certificate browsers accept (the WSS probe sends a status query through the agent's bridge).  Flow: a `host_server` account asks for a token (`POST /api/servers/tokens`, shown once, `AGENT_REGISTRATION_TOKEN=...`); the agent (`AGENT_REGISTRATION_URL`, `AGENT_PUBLIC_NAMES` first entry = game host:port, `AGENT_PUBLIC_URL` https or `AGENT_PUBLIC_WSS`) sends signed claims (`POST /api/servers/claim`) every 2 min while refused and every 10 min once accepted; a refused claim keeps the token, answers 422 with which probe failed, and records it on the token (shown on the account page).  Accepted = pending; an admin approves (it re-probes, so an unreachable server cannot be approved); `ProbeAll` runs every 3 min (`SERVERS_PROBE_MINUTES`) and a server is listed (`GET /api/servers?kind=official|community`, public, paged, official first) only while both probes pass.  Tickets and `/link` accept approved registry servers next to `TICKET_SERVERS`.  `probe` refuses non-public addresses (checked after name lookup and dialled by the checked IP), ports other than 443 and 1024-65535, and non-`wss`.  Limits: 5 servers+tokens per account by default (`SERVERS_MAX_PER_ACCOUNT`), and an admin can set another number for one account (`PUT /api/admin/accounts/{id}/server-limit`, `{"limit": n}` or null for the default; the "Server limit" button on a host's row in `/admin/`; table `server_limits`; audit action `server_limit`); an address can be registered once; admin actions go to the audit log.  Admin: `/admin/#servers` (approve, block, unblock, mark official = not probed, delete, add an official server by public key).  Local testing needs `SERVERS_DEV=1` (probe loopback, `SERVERS_PROBE_SECONDS`, `SERVERS_DEV_CA=<pem>` to trust a test CA); never in production.  **Joining from the browser:** the Join buttons link to `/play/?server=<server_id>`; `wasm/shell.html` (`communityBootInfo`, synchronous XHR) asks `GET /api/servers/<id>` (only a *listed* server answers; 404 otherwise), then uses its `wss_url` as the WebSocket endpoint and `+connect <game_addr>`.  The agent's claim carries the mod pk3 name (`pk3`, stored in `servers.pk3`); if it differs from the site's `/downloads/s4ndmod26/latest.txt` the page refuses with a message (the browser client plays with the site's own copy of the mod; fetching the server's pk3 is the later "mod from the server you join" step).  An unusable `?server=` sets `Module.noInitialRun` and shows the reason, never falling back to the official server.  Checked headless with a fake registry (`~/.cache/s4ndmod26-wasm/play` from `tools/local/build_wasm.sh`): the WebSocket url and `+connect` are right, bad/old/missing links start nothing.  **Decided (2026-11-13):** hosts bring their own domain and certificate; free random names are optional and later (see the plan).  **Not built yet:** the browser client using a registered server's address, purging a deleted server's stats.

**Stats from any server** (`stats/pull.go`, migration `008_server_id.sql`, `servers/005_stats_flag.sql`): the site pulls each approved server's `/v1/stats` (Range by byte offset) and `/v1/replays` from its agent (base = the wss host; `STATS_PULL_SECONDS`, default 60) into the same tables, tagged `games.server_id` (`''` = the local folder).  A pulled game's `match` is `<server_id>-<name on the server>` so names never collide; `src_match` is the server's own name.  The event feed is derived once per finished game: the `.rpl`+`.txt` go to a temp folder, are analysed and deleted (a replay that cannot be read is marked `-1` and not retried); the site never keeps a server's replays, the server and its agent serve them.  Community servers are fetched with a client that refuses private addresses; official ones (and `SERVERS_DEV=1`) may use private ones.  Admin: `POST /api/admin/servers/{id}/stats {on}` (per-server switch, default on), `POST .../purge-stats` (row id or server id) and `DELETE .../{id}?purge_stats=1` delete everything pulled from one server in one statement (cascades).  Official servers are also polled for hostname/map/players each probe pass.  Not done yet: pulled games have no replay link (a replay index + playback from the server's own address is the next step), and paths/fights/live views still read the local replay folder.

**Players and pools** (`stats/players.go`, `players_api.go`, migration `009_pid_pool.sql`): `game_players.pid` is the player's key (empty for bots/odd values), `games.pool` is stamped at first ingest (`official` for the local folder and official servers, `community` otherwise; later `comp-3v3` etc.).  `GET /api/players/{pid}` = totals and records per pool, `GET /api/players/{pid}/games?pool=&page=` = history (result judged by the last round: that round's winner vs the player's team; leaving before the round ended = `left`).  **Invariant: every aggregate is derived from `games`/`game_players`.**  `player_cache` (migration 010) holds a copy of each player's totals; anything that adds or deletes a player's games marks the row stale in the same transaction (`markStale`, and `PurgeServer` for everyone who played on the purged server), and `Player` recomputes a stale row on read while holding the row lock (`refreshPlayer`), so a purge (admin Purge, Delete or Block with `?purge_stats=1`) can never leave old numbers. **Identity answer vs the engine's flood protection** (found on the pr-113 preview): the engine ignores any client command (except `team`, `setspawnpt`, `score`) that follows another within 0.8 s (`sv_client.c`, `sv_floodProtect`), silently, and a client sends a burst at join, so the first `s4nd_auth` answer could be eaten: the player's console showed the answer, the server never logged `answered`, and their round-end line had no `pid`. Games already stored under such a name stay until purged and re-pulled.

**Changing the email address**: `POST /api/account/email {password, email}` mails a link to the NEW address (`/account/#email=`, 24 h, one pending change per account in `account_email_changes`, migration 009) and changes nothing until `POST /api/account/email/confirm {token}` is used; that works from any browser (no session), marks the new address confirmed, and sends a note to the old one.  Works for unconfirmed accounts too (fixing a typo).  The password is checked first; 10 tries an hour per account.  A wrong password answers "that is not your password" there (login keeps its own wording).  An address taken between request and confirm gives 409 and leaves the account as it was.

**Mail bounces**: Resend's webhook is `POST /api/mail/events` (Svix signature: HMAC-SHA256 of `id.timestamp.body` keyed with the base64 part of `ACCOUNTS_MAIL_WEBHOOK_SECRET`, `whsec_...`; 5 minutes of clock slack; the route only exists while the secret is set).  Events are recorded once by `svix-id` (`mail_events`).  A permanent bounce or a spam complaint sets `accounts.mail_bounced_at/mail_bounce_why` and switches the weekly summary off; three temporary bounces in a row (`mail_soft_bounces`, reset by `email.delivered`) do the same.  While marked, `SetDigest(true)` returns `ErrBounced` (409) and `DigestDue` skips the account; changing the email address (change-email confirm) clears the mark.  The account page shows why and disables the box; the admin list shows a "mail bounces" tag.  In the Resend dashboard the webhook needs `email.bounced` and `email.complained`; `email.delivered` is optional (it only resets the temporary-bounce count) and `email.delivery_delayed` is ignored.  Prod only: dev is not reachable from the internet.

**Passwords are typed twice**: the sign-up, change-password and reset-password forms on `/account/` have a "Repeat" field (`name="again"`), checked in the browser by `twice()` and never sent.  The server does not know about it (the API takes one password, as before).

**Visitor address behind the ingress**: nginx used to see only the cluster gateway (`10.42.0.1`) as the peer, so `X-Real-IP` was the same for everyone and every per-address limit in the API (sign-ups 5/h, logins, resets, demo uploads) was really one limit for the whole site.  `nginx.conf` now trusts `X-Forwarded-For` from `10.42.0.0/16` only (`set_real_ip_from`, `real_ip_header`, `real_ip_recursive on`: the rightmost untrusted entry wins), so the API gets the visitor in `X-Real-IP`.  A header a visitor sends cannot choose their address, and a request from outside the cluster range is taken at its peer address.  Checked with a real nginx 1.28 (Ubuntu build: `apt-get download nginx`, `dpkg -x`, run with a copy of the conf: trusted range 127.0.0.0/8, own temp/pid/log paths, `access_log off`) in front of a tiny echo server: direct, visitor in XFF, forged left entries, forged X-Real-IP, two trusted hops, and an untrusted peer.  The k3s pod range is the default 10.42.0.0/16 on both clusters (prod peer 10.42.0.1 from hostNetwork Traefik, dev peer a Traefik pod 10.42.0.x).

**Mail protections** (`accounts/mailguard.go`, migration 011): every confirmation, resend, address-change and reset mail takes from `reserveMail`: 3 mails a day to one address (`mailPerAddressDay`) and 30 an hour for the whole site (`ACCOUNTS_MAIL_PER_HOUR`, `Service.MailPerHour`; a warning is logged at 80%, and refused mail is logged).  Sign-up uses its allowance only after the account exists and removes the account again if the allowance is gone, so a failed sign-up cannot use up a stranger's.  Password resets only use the site-wide allowance (nobody can use up someone's way to recover an account) and are silently skipped, like for an unknown address.  Digest mails are not counted.  `mail_suppressed` holds addresses with a permanent bounce or a spam complaint for 30 days, kept even when no account has the address, so `Register` and the address-change form refuse them (400 "could not be delivered recently") and resets and the unconfirmed-account warning skip them.  Temporary bounces do not suppress.  Limits are in memory (a restart clears the counters; the suppression list is in the database).
